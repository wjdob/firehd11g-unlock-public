3. What this means for the LK load window (0x56000000-0x56900000)
-----------------------------------------------------------------
* Nothing is reserved between 0x54640000 and 0x624e0000, so the whole span
  0x56000000 -> 0x624e0000 (minus the ATF hole at 0x54600000, which is
  BELOW the window) is unreserved DRAM.  An oversized LK read that runs
  past 0x56900000 therefore does not clobber any reserved mblock until it
  reaches the framebuffer (0x624e0000), 0xe4e0000 past the window start.
* The preloader's own DRAM working set is BELOW the window:
  g_dram_buf = 0x44800000 (see stage2-unlock/README.md), footprint
  >= 0x44800000-0x448a3ac0.  An upward copy from 0x56000000 cannot reach it.
* Only identified preloader structure ABOVE the window is the MTK context
  save/restore slot at 0x5f100c00 (SP at +0x24, LR at +0x28, CPSR at +0x2c).

Because the preloader's block read is bounded by the *card*, not by the
partition, a read that starts at the lk partition and runs long walks
straight through tee1/tee2/metadata/... in order.  Mapping (destination =
0x56000000 + X, X = bytes read past the start of the LK partition):
  tee1     -> 0x56100000 ..
  recovery -> 0x5f400000 ..
  cache    -> 0x61bf0000 ..
i.e. only `recovery` and `cache` content can be steered into the
0x5f000000+ range where the 0x5f100c00 context slot lives, and neither is
writable while the bootloader is locked.  That is the blocker for turning
the oversized-read primitive into a control-flow hijack.
